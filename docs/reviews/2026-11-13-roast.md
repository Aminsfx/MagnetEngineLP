# Roast, 2026-11-13

Branch `fix/roast-2026-11-13`, cut from `main` at e85752b (what is deployed).
I read the Lead lifecycle and the numbers it feeds, the extension, the Edge
Functions and the UI. Every finding below has a failure scenario. The bugs I
could confirm are fixed, each test-first, one commit per bug or tight group.
The rest are left with a reason.

Already shipped and not re-reported: 1c6bd74 (the Inbox reader survives an
update and says when reading stopped) and bd64506 (Mark qualified).

## The short version

The code is careful about the things it has already been burned by, and
careless about the same class of mistake one layer over. Four bugs share one
pattern: **an error read as an empty answer.** A failed read looked like an
empty workspace (A), a failed write looked like a save (D), a failed plan read
looked like an unpaid plan (K), and failed follow-up sequences looked like
none (L). In each case the screen said something false and the Operator acted
on it: they saved the defaults over their own settings, lost edits on reload,
were sent to the checkout and asked to pay again, or edited ladders that
weren't theirs. Each fix is small. The rule it adds: a call that could not
answer must say so.

The worst bug was money (C). The paid gate lived only in the browser, so any
free sign-up could spend the Owner's AI and HikerAPI credit by calling the
functions directly. The most visible bug was the extension (B): an Inbox reply
sent during a campaign threw away every approved DM still queued.

### How each is fixed

- **C.** `servePost` takes `requireActivePlan`. The caller's `subscriptions.status`
  must be `'active'` (a trial is active, and spends through its allowance).
  Pending, cancelled or missing gets `403 subscription_inactive`. A row that
  can't be read gets `503 plan_unconfirmed`, and nothing is spent. The Owner
  (`ADMIN_EMAILS`) is never asked. The decision is in `_shared/access.ts`, with
  no Deno globals, tested from `src/lib/access.test.ts`. CLAUDE.md's Edge
  Functions seam now says every spending function passes it.
- **B.** `CAMPAIGN` carries an optional `mode`. `'add'` (Inbox replies, autopilot,
  follow-ups) puts the DMs at the front of the queue and leaves the campaign's
  progress, pause and last failure alone. `'replace'` (the default, which is all
  an older dashboard sends) keeps any added DM still waiting. Both are taken
  mid-send: the DM in flight finishes and nothing starts on top of it. A paced
  wait is respected rather than skipped, which the old code also got wrong. The
  same DM (handle + words) is never queued twice, nor beside the one being
  typed. The success alert is gone. This is backward compatible both ways, so
  no protocol bump: an old extension ignores `mode` and replaces, as before.
  It has unit tests (`src/lib/extensionQueue.test.ts`, the real `background.js`)
  and an e2e test in `e2e/extension/sender.e2e.ts`. Extension **1.10.1**.
- **A.** Reads throw (`readFailed`). The dashboard shows "We couldn't load your
  workspace" with Try again and saves nothing. The inbox load retries by itself
  (`src/lib/retry.ts`), and the Inbox says it is waiting.
- **D.** Writes throw after trying every batch. `useOutreach` runs every save
  through `persist`, which never rejects and says so once per burst
  (`src/lib/saveFailed.ts`). `addLeads` doesn't count unsaved Leads against the
  month, `removeMany` doesn't claim a delete that failed, and Write DMs stops at
  the first DM it can't keep. Settings, inbox and mark saves in the dashboard
  say the same.
- **K.** A failed read throws. `PlanContext.failed` holds it (access stays
  closed), and the gate shows "We couldn't confirm your plan" with Try again.
- **E.** A text-less message with content that wasn't unsent is kept as
  "[Sent an attachment: open it on Instagram]". Extension 1.10.1.
- **F/G.** Only a new message from them makes a Conversation unread, and an
  answer makes it read. Photos are compared by path, and the fresh URL is still
  the one kept in memory.
- **H/J.** The card dates the mark, and the button says "Mark qualified".
- **L.** Any id starting `new` is inserted without an id, and the database
  names it. A uuid's hex never starts with `n`. `getSequences` throws, and the
  page says "We couldn't load your follow-up sequences" with Try again,
  seeding nothing. The local adapter keeps its `new-` ids: it stores them as
  they are, one per ladder, and changing that would duplicate rows local
  workspaces already hold. This is confirmed against the schema in CLAUDE.md
  (`id uuid`). If the live table's `id` were text, the save would have worked
  and only the load half of this fix would matter.

## Left as findings

### Real, but a decision or a bigger change than a fix

1. **Sent is per browser, not per Operator.**
   - **Where:** `extension/background.js:123-140` (SESSION), `:382` (`sentHandles`).
   - **What happens:** `sentHandles` and `sentLog` survive a different
     dashboard user signing in, and the next STATS marks that user's Leads
     with the same handles as Sent.
   - **Why left:** clearing them per user is wrong for the Owner's own setup:
     two logins share one Instagram account, and a second workspace would DM
     the same people again. The right key is the Instagram account
     (`inboxViewer.id`), not the dashboard user. That is a design call, not a
     one-line fix.
2. **Lead writes are whole documents, last writer wins.**
   - **Where:** `src/lib/db.ts:228`.
   - **What happens:** two tabs, or a tab and the extension bridge, each write
     the whole `data` jsonb, so a change made in one tab can be overwritten by
     an older copy of the Lead from the other.
   - **Why left:** fixing it needs field-level patches or a version column, a
     schema change (also noted on 2026-11-10).
3. **`generate-reply` has no quota, and both generators take any system prompt
   from the client.**
   - **Where:** `generate-reply/index.ts:133`; `generate-dm/index.ts:92`,
     `generate-reply/index.ts:134`.
   - **What happens:** since C, only paying accounts can call them. But one
     paying account can still use `generate-reply` as an unmetered general
     LLM proxy.
   - **Why left:** a reply quota (`MONTHLY_REPLY_LIMIT`, metered like
     `dm_usage`) needs a migration and a limit only the Owner can choose.
4. **The DM quota is check-then-increment.**
   - **Where:** `generate-dm/index.ts:108` reads `used`, `:236` increments.
   - **What happens:** parallel calls all pass the check, so a scripted
     client can overshoot 1,500.
   - **Why left:** bounded now by the plan gate. The fix is a reserve-first
     RPC (increment, then refund on skip or failure), which is a migration.
5. **A failed save leaves the change on screen.** The toast says so (D), but
   nothing is rolled back. Rolling back cleanly races with later edits, and
   telling the Operator was the part that was missing.
6. **A reply added to a paused campaign waits for Resume.** I chose this in
   B on purpose: the old behaviour (any handoff un-pauses everything) would
   now restart a paused 200-DM campaign because of one reply. The Inbox shows
   the reply as queued either way.

### Plausible, not confirmed without real payloads or a second tab

7. **Message requests and the General folder are probably not read.**
   - **Where:** `extension/igpage.js:27`.
   - **What happens:** only `PolarisDirectInboxQuery` is replayed, which is
     the Primary folder.
   - **To confirm:** capture one real response from the Requests tab.
8. **Polling needs the page to have loaded `/direct/` once.**
   - **Where:** `extension/igpage.js:37,104`.
   - **What happens:** the replay template is only learnt from a live
     request, so an Instagram tab that never opened the inbox reads nothing.
   - **Why left:** storing the template would put Instagram's request
     headers in extension storage, which is worse than the gap.
9. **Two patches in one tick read the same stale `leadsRef`.**
    - **Where:** `src/lib/useOutreach.ts:195,241`.
    - **What happens:** `leadsRef` refreshes in an effect, so a handler that
      calls `approve` then `updateDM` before a render bases the second on the
      pre-approve Lead and drops the approval.
    - **Status:** no caller does this today that I found.
10. **Settings save on every keystroke.**
    - **Where:** `SettingsPanel.tsx:657,783,825,855`.
    - **What happens:** each keystroke is its own write, and writes can land
      out of order, so the stored prompt can be a few characters behind what
      the Operator typed.
    - **Fix:** debounce, or save on blur.

### Taste, product, hygiene

11. **Marks can't be undone.** Qualified and Booked in the Inbox
    (`OpenConversation`) are one-way. An Operator who clicks the wrong row has
    no way back short of editing the Lead.
12. **The 'always' follow-up condition reaches Booked and Won Leads.**
    - **Where:** `src/lib/followups.ts:159`.
    - **What happens:** a customer can get "still keen?". No default ladder
      uses `always`. It is a sharp edge for an Operator who picks it.
13. **The Copilot spends three AI calls each time a conversation is opened.**
    - **Where:** `src/components/inbox/Copilot.tsx:63`.
    - **Status:** unmetered. Fine for now; it is the first thing to look at
      if AI cost climbs.
14. **Size.** `DashboardShell.tsx` is still over 900 lines and owns the inbox
    log, the extension bridge and every handler. `extension/background.js`
    is one 700-line listener. `src/pages/LandingPage.tsx` is unrouted dead
    code that CLAUDE.md has to warn about.
15. **Lint.** 10 warnings on `main`, the same 10 on this branch, with none
    added: react-refresh/only-export-components and
    react-hooks/set-state-in-effect in `PlanContext` and `AdminPage`, among
    others.
16. **Operator-facing copy that points at the console.** The Follow-ups page
    answers a failed Save with "Save failed — check console"
    (`FollowUpSequencer.tsx:214`). An Operator has no console, and
    `upsertSequence` already logs the real cause. Better: say the change wasn't
    saved and to try again.

  Every commit was typechecked and unit-tested as it landed.

  so `http.ts` was checked by reading and its decision by

  staging to exercise them.

## Only the Owner can do these

From the project folder:

```bash
supabase functions deploy generate-dm --use-api
supabase functions deploy generate-reply --use-api
supabase functions deploy scrape --use-api
```

Deploy the dashboard as usual, then build and upload extension 1.10.1 to the
Chrome Web Store (`npm run ext:zip`). The dashboard and functions are safe to
ship before the extension. An old extension ignores the new `mode` and behaves
as it does today. No migration.
